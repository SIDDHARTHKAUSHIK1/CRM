# Master Prompt — Multi-Tenant Data Isolation ("Account A never sees Account B") for this Krayin-based Laravel CRM

Paste everything below to your coding agent as-is (Claude Code, Cursor, etc.), in the root of this repo, with full file read/write access and shell access (`php artisan`, `composer`, `npm`). This is a large, cross-cutting change — the agent should work module-by-module and re-run the validation checklist at the end after every module, not just once at the very end.

---

## 0. Naming decision — read this before writing a single line

The word **"Account"** is already used in this codebase for something else: `packages/Crm/Admin/src/Http/Controllers/User/AccountController.php` is the logged-in user's own "My Account" profile-edit page. The word **"Organization"** is also already taken: `Crm\Contact` has an `organizations` table, which is a CRM contact/company record (e.g. "Acme Corp" as a lead's employer), not a tenant.

To avoid a confusing collision with either, this feature introduces a new concept called a **Tenant**: `tenants` table, `Tenant` model, `tenant_id` foreign key. Do not call it "Account" or "Organization" anywhere in code, table names, routes, or variable names, even though the person who requested this feature used the word "account" in conversation — translate that to "tenant" everywhere in the implementation. Every "user account" in the original request = a `users` row; every "account" that must be isolated = a `tenants` row that one or more `users` rows belong to.

## 1. Context — study these real files before changing anything

This is a Laravel 12 CRM built on the Krayin package architecture, rebranded from `Webkul\*` to `Crm\*`, with ~20 packages under `packages/Crm/*`. Guard name is `user` (see `config/auth.php`), not `web`. It's deployed at a Hostinger VPS via `deploy.sh` (first install) / `update.sh` (redeploy, which runs `php artisan migrate --force` then `npm run build` at root and inside `packages/Crm/Admin`), and also run locally via `php artisan serve`. There is **already a real user base and real production data on the live VPS** — every migration you write must be a safe, additive, zero-downtime migration (add nullable column → backfill data → tighten constraint in a later step), not a destructive rebuild. Confirmed real files/schemas (do not guess — re-read the actual file if anything below looks stale by the time you work, this codebase is under active development):

- `packages/Crm/User/src/Models/User.php` — table `users` (columns confirmed in migration: `id, name, email (unique), password, status, role_id, remember_token, timestamps`, plus `image`, `password_plain`, `last_login_at`, `view_permission` added in later migrations — check `packages/Crm/User/src/Database/Migrations/` for the exact current list before writing your own migration).
- `packages/Crm/User/src/Models/Role.php` — table `roles`: `id, name, description, permission_type ('all'|'custom'), permissions (json)`.
- `packages/Crm/User/src/Models/Group.php` + pivot `user_groups` — an existing team/visibility-group concept (Settings → Groups) used together with `users.view_permission` (`all`/`group`/`individual`) to control which leads a given employee can see *within one shop*. This is a real, working feature already — do not remove or fight it, just make sure it becomes tenant-aware (see §5).
- `packages/Crm/Admin/src/Http/Middleware/Bouncer.php` — the login-session guard middleware (checks `auth()->guard('user')->check()`, active status, non-empty permissions).
- The **separate** `bouncer()` facade/helper (`packages/Crm/Admin/src/Http/helpers.php` and its backing class — locate it, it's not the middleware above) exposes `bouncer()->hasPermission('key')` and `bouncer()->getAuthorizedUserIds()`. The latter is used directly in `Crm\Lead\Repositories\LeadRepository::getLeadsQuery()` to restrict which `leads.user_id` values are visible based on the current user's role/group visibility. **Read its implementation and confirm it will still return only same-tenant user ids once roles/groups are tenant-scoped** — it should, transitively, but verify it, don't assume.
- `packages/Crm/Core/src/Eloquent/Repository.php` — thin wrapper around `Prettus\Repository\Eloquent\BaseRepository` (the `l5-repository` package). Every module repository (`LeadRepository`, `PersonRepository`, `ProductRepository`, etc.) extends this. This matters because it means the cleanest scoping primitive is a **native Eloquent global scope on each model**, not a change to this shared base class — a global scope automatically applies to every `find`, `findOrFail`, `paginate`, `scopeQuery()` closure, etc. that these repositories already use, with zero change to repository code.
- `packages/Crm/DataGrid/src/DataGrid.php` — the base class for every listing/table screen in the admin panel (leads list, contacts list, quotes list, etc., one concrete subclass per screen, e.g. `LeadDataGrid`, `UserDataGrid`). **This is the one place Eloquent global scopes will NOT save you**: `prepareQueryBuilder()` in concrete subclasses builds a raw `Illuminate\Database\Query\Builder` via `DB::table(...)`, which is a completely different query builder than Eloquent's and is invisible to Eloquent global scopes. Every DataGrid subclass needs an explicit tenant filter added by hand (see §5.2). Run `grep -rl "extends DataGrid" packages/` to get the authoritative, current list — do not rely on the module list in this document, it may be incomplete or stale by the time you implement this.
- `packages/Crm/Installer` — a **one-time server-provisioning wizard** (`InstallerController`, `installer/index.blade.php`, seeders under `Database/Seeders/{Attribute,Core,EmailTemplate,Lead,User,Workflow}`), not a per-tenant signup flow. It seeds exactly one Administrator role/user, one default lead pipeline/stages/sources/types, one set of default attributes, one set of default email templates — all currently global, singular, unscoped. Every new tenant created after this feature ships needs an equivalent per-tenant seed of pipeline/stages/sources/types/attributes/email-templates — reuse these exact seeder classes (parameterized by `tenant_id`) rather than writing new ones from scratch.
- `packages/Crm/Admin/src/Http/Controllers/User/SessionController.php` — the one single login form/flow for every user regardless of tenant (do not create a second login page or a subdomain-per-tenant scheme — tenant is resolved from `auth()->guard('user')->user()->tenant_id` after login, not from the URL).

Grep every `core()->get('...')` / `SystemConfig` read call across the codebase and classify each key as "install-wide" (stays global) or "per-tenant" (needs scoping) — do not assume, list them out for the person running this to confirm.

## 2. The `tenants` table and `Tenant` model

New package or a small addition to `Crm\Core` (agent's call — a full new `Crm\Tenant` package is cleaner given this codebase's module-per-concern convention, but a lighter touch inside `Crm\Core\Models` is acceptable if you keep it equally clean). Minimum columns: `id, name, status (active/suspended, default active), created_at, updated_at`. Do not add billing/plan/subdomain columns unless the person running this asks for them later — keep this feature scoped to isolation, not a full SaaS billing system.

## 3. `users.tenant_id` and the login/email-uniqueness decision

- Add `tenant_id` to `users`, backfilled to a single pre-existing "Default Tenant" row (create it in the same migration or a seeder run right before) so the live production data on the VPS has zero orphaned rows, then make it `NOT NULL`.
- **Keep `users.email` globally unique across the whole install** (do not change the existing `unique:users,email` validation in `AccountController::update` or `UserController::store/update` to a composite `(tenant_id, email)` unique). Reasoning: there is one login form and one `user` guard for the entire application — a globally unique email keeps "log in with your email" unambiguous. If the person running this specifically wants two different tenants to be able to register the same email address as two separate accounts, flag that as a distinct, bigger change (composite unique index, and `attempt()` would need to disambiguate by more than email+password) — do not build it speculatively.
- `Role` and `Group` gain `tenant_id` too (see §1 table). `RoleRepository`/`GroupRepository`/their settings controllers and datagrids need the same two-layer scoping as everything else (§5).

## 4. Tenant resolution — how "current tenant" is determined on every request

Because every user belongs to exactly one tenant (no subdomain-per-tenant, no header, no query param), tenant resolution for an authenticated admin-panel request is simply: **`auth()->guard('user')->user()->tenant_id`**. Implement:

- `current_tenant_id()` helper function, added to `packages/Crm/Core/src/Http/helpers.php` next to the existing `bouncer()`/`acl()`/`menu()` helpers, following that file's exact style. It should read from a small request-scoped cache (a static property or a singleton bound in a service provider — `TenantContext` class) rather than re-querying `auth()` every call, since it will be called from dozens of places per request.
- **Queued jobs have no authenticated user — this is the case most likely to silently break.** `grep -rl "ShouldQueue" packages/` to find every queued job (expect hits in `Crm\Automation`, `Crm\Marketing`, `Crm\DataTransfer`, `Crm\WhatsApp` at minimum). Each one must carry `tenant_id` as an explicit constructor property (it gets serialized with the job automatically), and `handle()` must explicitly push that tenant_id into `TenantContext` before touching any repository. **Do not assume the global scope alone covers this** — if `current_tenant_id()` silently returns `null` inside a job, a naive global scope implementation will produce a `WHERE tenant_id IS NULL` query that just returns zero rows with no error, which looks like "it works" in a quick manual test but is actually silently broken. Write an explicit failing-then-passing test for at least one job in each of those four packages.
- **Unauthenticated/public endpoints have no `auth()->user()` at all.** `Crm\WebForm`'s public submission endpoint is the clearest example — grep `routes/` and every package's `Routes/*.php` for routes that are *not* behind the `user` guard/Bouncer middleware, and resolve tenant explicitly from the entity being acted on for each one (for WebForm: `$webForm->tenant_id`, looked up by the form's own route key, before the tenant-scoped `Lead`/`Person` create calls happen). List every such route you find in your final summary — don't assume WebForm is the only one; WhatsApp inbound webhooks are a likely second case.

## 5. The two-layer enforcement mechanism (build both, this is not optional)

### 5.1 Model layer — Eloquent global scope

- One trait, `BelongsToTenant` (e.g. in `Crm\Core\Traits`), applied to every model listed in §1's table. In its `bootBelongsToTenant()`: register a global scope that adds `->where($model->getTable().'.tenant_id', current_tenant_id())` to every query, and a `creating` model event that sets `$model->tenant_id = current_tenant_id()` if not already set.
- This single trait, once applied, automatically protects every `Repository::find/findOrFail/paginate/scopeQuery()` call across every module, because Prettus's `BaseRepository` ultimately runs everything through the Eloquent model's query builder. **Verify this specifically for `LeadRepository::getLeadsQuery()`**, which builds a query via `->scopeQuery(fn ($query) => ...)` with manual `leftJoin()` calls — confirm empirically (two tenants, two leads, log in as each) that the scope still applies before trusting it, since this method selects raw columns and joins other tables rather than doing a plain `Model::query()`.
- Also verify direct `Model::find($id)` / `Model::where('id', $id)->first()` calls that bypass the repository layer entirely (`grep -rn "::find(\|::findOrFail(\|::where('id'" packages/*/src/Http/Controllers`) — they're still protected by a *global* scope (global scopes attach to the model class itself, not to a specific repository instance), but confirm this is true for every hit, since a controller could theoretically call `Model::withoutGlobalScope(...)` or a raw `DB::table()` call instead of the Eloquent model.

### 5.2 DataGrid layer — raw query builder, needs an explicit line per class

Add a small helper (either a trait `TenantScopedDataGrid` or a protected method on the base `Crm\DataGrid\DataGrid` class itself — the base class is a good home since every concrete DataGrid already extends it) — e.g. `protected function scopeToCurrentTenant($queryBuilder, string $table = null)` that adds `->where(($table ?? $this->primaryTable).'.tenant_id', current_tenant_id())`. Then, in every concrete DataGrid subclass's `prepareQueryBuilder()` (get the authoritative list via `grep -rl "extends DataGrid" packages/` as noted in §1 — expect one per listing screen: leads, contacts/persons, organizations, products, quotes, activities, users, roles, groups, tags, web forms, workflows, campaigns, imports, warehouses, and more), add one call to this helper. This is mechanical but must be done for every single one — missing even one means that one listing screen silently leaks cross-tenant rows while everything else looks correctly isolated, which is a dangerous "mostly fixed" state. Track the full list you found and the full list you fixed in your final summary and confirm they match exactly.

### 5.3 Route-model-binding / direct-URL-access layer

Even with both layers above, explicitly test that opening `/admin/leads/{id}/edit` (or contacts, quotes, products, etc.) for an ID that belongs to a different tenant returns a 404 (via the global scope making `findOrFail` genuinely fail to find the row), not a 403 with any information about the record's existence, and not the record itself. This should fall out of §5.1 automatically — the test is to prove it, not to write new code, unless the test fails, in which case that controller has a bypass you need to find (see the `grep` in 5.1).

## 6. New-tenant provisioning — a real open decision, don't silently pick one

There is currently **no way to create a second tenant at all** — `Crm\Installer` is a one-time whole-install wizard, and "Settings → Users" only creates users inside the *current* tenant. Multi-tenant isolation is unreachable/untestable until something can create tenant #2. Two real options — tell the person running this which you're building and why, don't just silently choose:

- **Option A — Artisan command, no public signup** (recommended starting point): `php artisan tenant:create "{name}" {admin_email} {admin_password}` creates one `tenants` row and one `users` row (`role_id` pointing at a freshly-seeded per-tenant Administrator role, `permission_type = 'all'`), then runs the exact same seeding logic as `Crm\Installer`'s `Lead`, `Attribute`, and `EmailTemplate` seeders, parameterized to the new `tenant_id`, so the new tenant gets a working default pipeline/stages/sources/types/attributes/templates instead of an empty, broken-looking CRM. Smallest safe surface area — no new public route, no new attack surface, and it's enough to fully prove isolation works end-to-end.
- **Option B — public self-serve "Sign Up" page**: bigger scope — a new unauthenticated route (outside the `user` guard/Bouncer middleware, so treat it like the WebForm case in §4/§6 for tenant-resolution purposes — there is no tenant yet, one is being created), its own validation/rate-limiting, and the same per-tenant seeding as Option A, run inside the same DB transaction that creates the tenant and its first user.

Default to building **Option A** unless the person running this says they need public signup now — it fully exercises and proves the isolation mechanism with far less new surface area, and Option B can be layered on afterward without touching anything in §4/§5.

## 7. WhatsApp — flag as a separate, bigger decision, don't quietly half-do it

`whatsapp-gateway` (top-level directory, a separate Node/Baileys service) almost certainly represents **one physical WhatsApp Business number/session for the whole install today**. Adding `tenant_id` to `whatsapp_campaigns`/`whatsapp_do_not_contacts` (per §1) isolates the *data* (which tenant's campaign/recipients/opt-outs) but does **not** give each tenant their own WhatsApp number — every tenant's outbound messages would still send from the same shared number, and inbound messages need a routing rule to know which tenant they belong to. True per-tenant WhatsApp (separate paired numbers/sessions) is a materially larger feature (per-tenant Baileys session management, per-tenant QR pairing UI, per-tenant gateway process or multiplexed session store). For this pass: scope the data as listed in §1, but explicitly tell the person running this, in your final summary, that the WhatsApp *number* itself is still shared across tenants until a separate Phase 2 is built — do not imply WhatsApp is fully isolated when only the campaign records are.
