## What "admin" and "employee" mean here — resolve this before coding

There is (correctly) only **one** login form. "Login as employee" / "login as admin" in the requirements below does **not** mean two different login pages — it means: after the *same* login form authenticates someone, the app must visibly say which kind of account just logged in, everywhere in the admin panel header, for the rest of that session. Implement it exactly like this:

- **Admin** = `$user->role && $user->role->permission_type === 'all'` (matches `Bouncer.php`'s own definition — do not diverge from it).
- **Employee** = any other authenticated `user` (i.e. `role->permission_type === 'custom'`), regardless of what the shop owner names that role ("Employee", "Agent", "Sales Executive", etc.). Do not hardcode a role name anywhere in PHP or Blade logic.

## Feature list to build

1. **Role badge in the header, on every admin-panel page, both themes.**
   In `components/layouts/header/index.blade.php`, add a small pill/badge immediately to the left of the existing "Admin profile" dropdown (or directly beside the logo — your call, but it must be visible without scrolling on both desktop and the mobile header), reading **"ADMIN"** or **"EMPLOYEE"** based on the check above. Requirements:
   - Bright, high-contrast, unmistakable at a glance — not a subtle gray label. Suggested classes (adjust to match this project's existing color tokens, check `tailwind.config.js` for the actual `brandColor`/semantic colors already defined and reuse them rather than inventing new hex values):
     - Admin: `bg-red-600 text-white dark:bg-red-500 dark:text-white` (or the project's existing "danger/important" color if one exists — grep other blade files for how they already flag "important"/"admin-only" badges and reuse it).
     - Employee: `bg-blue-600 text-white dark:bg-blue-500 dark:text-white`.
   - Rounded pill, bold uppercase text, small icon optional (e.g. a shield icon for admin) — check the existing icon font (`resources/**/*.css` or wherever `icon-setting` etc. are defined) for a suitable existing glyph before inventing a new one.
   - Must pass basic contrast in both light and dark mode — do not rely on a low-contrast tint; verify by eye against both `bg-white`/`dark:bg-gray-900` header backgrounds.
   - Also show the same badge (smaller) in the profile dropdown next to the user's name, and on the "My Account" edit page, so it's unambiguous everywhere, not just the header.

2. **Only admins can create employee accounts.**
   - The existing "Settings → Users" create/store/update/delete actions are already gated by ACL keys (`settings.user.users.*`). Make sure the **only** role allowed to hold those permission keys by default is the Administrator (`permission_type = 'all'`) role — a `custom` role must never be able to see or reach `admin.settings.users.*` routes unless the admin explicitly grants it, which is already how the ACL/role system works. Do not weaken or bypass this — just confirm it (write a quick manual test: log in as a custom-role user with no `settings.user.*` permission checked and verify "Settings" menu doesn't expose Users/Roles/Groups/Employees at all, and hitting the URL directly redirects/403s).
   - In `UserController::store()` / `update()`, when the acting admin is *not* an admin themselves (defense in depth, in case ACL is ever misconfigured), reject the request server-side too — add a check at the top of both methods: if `! (auth()->guard('user')->user()->role->permission_type === 'all')` then `abort(403)`. This is a belt-and-braces check on top of the existing ACL gate, not a replacement for it.

3. **New "Employees" admin-only section** (separate from, and in addition to, the existing generic "Settings → Users" page — that page still exists for creating accounts/assigning roles; this new page is the oversight/management console the admin specifically asked for).
   - New ACL key `settings.user.employees` (+ `.index`, `.edit_password`, `.reveal_password`, `.delete`) in `acl.php`, new menu entry in `menu.php` under the `settings.user` group (same pattern as `settings.user.users`), new named routes `admin.settings.employees.*` added to `settings-routes.php` next to the existing `users` route group, new controller `packages/Crm/Admin/src/Http/Controllers/Settings/EmployeeController.php`, new views under `Resources/views/settings/employees/`, new `EmployeeDataGrid.php` mirroring `UserDataGrid.php`.
   - **Hard-gate every route and every controller method in this new section** with both the ACL check (via the route being present with the right key in `acl.php`, exactly like every other settings route) **and** an explicit `if (! $currentAdmin->role || $currentAdmin->role->permission_type !== 'all') abort(403)` at the top of every controller method — this section must be unreachable by anyone but a full admin even if the ACL config is ever hand-edited incorrectly.
   - The listing shows every account **except** the currently-logged-in admin's own row (an admin manages other people from here, not themselves — "My Account" already covers self-editing) and, if you want, you may include other admins too but flag them distinctly (don't let one admin silently reset another admin's password without at least a visual "this is an admin account" warning — reuse the ADMIN/EMPLOYEE badge here too).
   - Columns/info to show per row: name, email, role name, status (active/inactive), created date, **last login timestamp** (new — see schema below), and a rough "work" summary: count of leads, quotes, and activities currently attributed to that user (`Crm\Lead\Models\Lead` has a `user_id`/owner column, `Crm\Quote\Models\Quote` likewise, `Crm\Activity\Models\Activity` has a `user_id` — grep each model's migration for the exact FK column name before writing the query; do not guess the column name, confirm it in the actual migration file for each of those three packages).
   - Row actions, each independently permission-checked exactly like `UserDataGrid::prepareActions()` already does:
     - **Edit** → opens a form to change name/email/status/role (same validation as `UserController::update`) and set a new password (see password rules below).
     - **Reveal password** → see the dedicated security section below, this is not a simple "show a column."
     - **Delete** → same safeguards as `UserController::destroy` already has (`$this->userRepository->count() == 1` blocks deleting the last account) **plus** two more you must add: block deleting your own account from this page, and block deleting the last remaining `permission_type = 'all'` account (there must always be at least one admin left, or the shop owner locks themselves out).

4. **Admin can view an employee's actual password, and can set a new one.** This is the one part of the request that fights normal security practice — read this whole section before writing code, then implement it exactly as specified so it's as safe as this feature can be made:
   - Laravel's `password` column is a one-way bcrypt hash — **it is mathematically impossible to recover the original password from it**, for anyone, including you. To satisfy "admin can see the employee's password," the only honest option is to *also* store a second, separately-encrypted copy of the plaintext, and decrypt that copy on demand. Implement it this way:
     - New nullable `text` column `password_plain` on `users` (migration in `packages/Crm/User/src/Database/Migrations/`, timestamped after the existing ones, following the exact same file-naming and `Schema::table('users', ...)` pattern as `2021_11_12_171510_add_image_column_in_users_table.php`).
     - Whenever `UserController::store/update` **or** the new `EmployeeController`'s password-set action sets a new password, write **both** columns in the same request: `password` = `bcrypt($plain)` (unchanged, still what login checks), `password_plain` = `Crypt::encryptString($plain)` (Laravel's `Illuminate\Support\Facades\Crypt`, AES-256-CBC keyed off `APP_KEY`). Never derive one from the other — always encrypt the plaintext the admin actually typed, at the moment it's set.
     - Add `password_plain` to `User::$hidden` immediately, so it is **never** accidentally serialized into any JSON response, datagrid row, or API resource by default.
     - The reveal action is a dedicated endpoint, `POST admin.settings.employees.reveal_password` (or nested under the employee's id), that: (a) is admin-only per the double-gate above, (b) requires the **requesting admin's own current password** to be submitted and verified with `Hash::check()` before it does anything (password re-confirmation — do not skip this, it's the one thing standing between "admin panel" and "anyone at the admin's unlocked laptop"), (c) then returns the decrypted plaintext as a small JSON response consumed by a bit of Alpine/Vue JS that fills a "click to reveal" field — never render the decrypted password server-side into the initial page HTML/DOM, only fetch it on an explicit click, (d) writes a log line (`Log::info` or, better, use the existing `Event::dispatch` pattern this codebase already uses everywhere else, e.g. `Event::dispatch('user.admin.password.revealed', [$requestingAdmin->id, $targetUser->id])`) so there's an audit trail of who viewed whose password and when.
     - Rate-limit this endpoint (Laravel's `throttle` middleware, e.g. `throttle:10,1`) so it can't be hammered.
     - Tell the person running this project, in your final summary to them, two operational facts they must know: (1) if `APP_KEY` in `.env` is ever changed/regenerated on either environment, every existing `password_plain` value becomes permanently undecryptable garbage — do not run `php artisan key:generate` on an environment with real employee data without a plan for this; (2) storing recoverable passwords at all is a real security trade-off (a database leak now exposes live, usable passwords instead of just hashes) — this was built because it was explicitly requested, but consider whether "admin can force-reset an employee's password" (which you're also building, see next bullet) actually covers the real need without keeping plaintext around at all.
   - **Setting a new password for an employee** (the safer, always-available alternative/complement to revealing the old one) is just the existing update-password flow, reused: same validation as `UserController::update` (`password nullable|string|min:6` + confirm), same "write both `password` and `password_plain`" logic above.

5. **"Track their work"** — on the same Employees page (or a per-employee detail view, your call based on how much fits cleanly), show, per employee: last login date/time (new `last_login_at` timestamp column on `users`, set in `SessionController::store()` right after a successful `auth()->guard('user')->attempt()` and the existing status check, via `auth()->guard('user')->user()->update(['last_login_at' => now()])`), and counts of leads/quotes/activities currently assigned to them (query the real FK columns you confirmed in step 3). Do not build a heavier "activity feed"/audit-log system beyond this unless you find one already half-built in `packages/Crm/Activity` that's trivial to reuse — check first.

6. **This must work identically on localhost and on https://realestate.aflix.co.in/.**
   - No hardcoded domain, scheme, or port anywhere in your PHP or JS — use `route()`, `url()`, `config('app.url')`, relative asset paths via `vite()->asset(...)` exactly like every existing file already does. Grep your own new files for the literal strings `localhost` and `realestate.aflix.co.in` before finishing — there should be zero matches outside of comments.
   - Session/cookie behavior: don't introduce any new cookie or session key without checking `config/session.php` — reuse the existing `dark_mode`-cookie style (`path=/`) if you add any client-side cookie at all (you shouldn't need one for this feature).
   - New Vite/JS you add for the "reveal password" click-to-fetch behavior must be built the same way existing inline `@pushOnce('scripts')` Vue components in this codebase are (see the `v-dark` component in the header file) — do not add a new bundler entry point or an npm package.
